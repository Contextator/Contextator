Privacy Policy

Last updated: 18 September 2026

Contextator is self-hosted software. It has no analytics and no telemetry: it never reports anything back to its authors, and the people who wrote it have no access to any data in your installation. It does manage user accounts — but those exist only inside your own installation, and nothing about them leaves it.

1. Two different things

This policy covers the Contextator software — the server and dashboard you are looking at — and the product website at contextator.com. It does not cover the installation you are using if somebody else runs it: in that case the operator of this instance decides what is stored, for how long and who may see it. Ask them, not us.

2. What the software stores

Everything below is written to the database and disks of the machine running this instance, and nowhere else:

  • Projects and sources — names, paths, repository URLs, branches, Notion root ids, file-type and content-type settings.
  • Indexed documents and their embeddings — the text of every file that was indexed, split into chunks, plus the vector of each chunk.
  • Materialised sources — uploaded files and archives, git checkouts and Notion pulls, kept in the data directory so that runs can be incremental.
  • Index run history — start and finish times, file and chunk counts, and the error message of a failed run.
  • Access tokens for private git repositories and Notion integrations — encrypted at rest with AES-256-GCM using the deployment's SECRET_KEY, never returned by the API and never displayed again after they are saved. Credentials pasted into a repository URL are stripped before the URL is stored.
  • Webhook secrets, one per git source, used to verify that a push notification really came from the provider.
  • User accounts — a username, an optional display name and e-mail address, the role (root, admin or member), whether the account is active, when it was created and when it last signed in.
  • Password hashes — passwords themselves are never stored. Only a salted scrypt hash is kept, and it cannot be turned back into the password. Passwords never appear in the logs, and the API never returns one.
  • Sessions — one row per signed-in browser: a hash of the session token (not the token), the browser's user-agent string, the IP address the session was opened from, when it started and when it was last used.
  • Project memberships — which account may read, and which may change, which project.

Deleting a project or a source deletes its documents, chunks, embeddings and materialised files. Deleting a user account deletes its sessions and memberships immediately; documents that person uploaded belong to the project and stay with it. Signing out, changing a password and "sign out everywhere" each delete the sessions they end. The database and the data directory are ordinary volumes: backups, retention and access control are the operator's responsibility.

3. What your browser stores

After you sign in, the dashboard sets one cookie, contextator_session. It holds an opaque session id, is HttpOnly and SameSite=Lax, and is deleted when you sign out. Nothing else is kept in the browser: the localStorage key that older versions used for the admin token is gone, and the dashboard clears any leftover automatically. Details are on the Cookie Policy page.

4. Logs

The server writes operational logs to standard output: startup information, index run progress and errors. Per-request HTTP logging is off unless the log level is set to debug or trace. Where those logs go and how long they are kept is decided by whoever runs the container.

Failed sign-in attempts are logged with the username that was tried and the address it came from, so an operator can see an attack in progress; account creation, password resets and deletions are logged with the administrator who did them. Passwords, password hashes and session tokens never reach the log.

5. When data leaves the machine

A default installation makes exactly one kind of outbound call, and only once. The rest happen only if you configure them:

  • Embedding model download. On first start the local embedding model (~470 MB) is downloaded from the Hugging Face CDN. Set EMBEDDING_OFFLINE=1 with a pre-populated model cache to avoid it entirely.
  • OpenAI embeddings — optional. If the deployment sets the embedding provider to OpenAI, the text of every chunk that is indexed and every search query is sent to the OpenAI API under your own API key and their terms. The local provider sends nothing.
  • Your own sources. Git hosts you add are contacted to clone and fetch; Notion is contacted to read the pages shared with your integration. Both use the credentials you provided.
  • Web fonts. The dashboard and these pages load typefaces from Google Fonts, so your browser contacts fonts.googleapis.com and fonts.gstatic.com, which receive your IP address and user agent. Self-host the fonts if you would rather it did not.

There is no usage tracking, no crash reporting and no update check.

6. Who can see what

An account is one of three roles. root and admin reach every project and manage accounts; a member reaches only the projects it has been added to, as a viewer that reads or an editor that can add sources, upload files and re-index. Every one of those rules is enforced on the server, not in the browser.

Accounts do not protect the MCP endpoints. /mcp/<project> is unauthenticated by design, so anyone who can reach that URL can read that project's indexed documents whatever their role here — or without an account at all. Membership governs the dashboard and the admin API. Keep the server on a private network, or put it behind a reverse proxy that authenticates.

7. MCP clients

An AI agent connected to /mcp/<project> receives the excerpts and documents it searches for, and whatever the agent does with them is governed by that client's own privacy policy. The MCP endpoints are unauthenticated by design, so anyone who can reach the URL can read that project's indexed documents. Keep the server on a private network, or put it behind a reverse proxy that authenticates.

8. Personal data

Contextator is a documentation indexer; it does not profile anyone. The names and e-mail addresses of the people you give accounts to are personal data, and so is anything personal inside the documents you index. In both cases you are the controller and this software is a processor running on your own hardware — the usual duties (lawful basis, retention, deletion, access requests) stay with you.

9. The product website

contextator.com is a separate, static product site. It is served with no advertising and no cross-site tracking; any server-side request logs it keeps are used only to operate the site and to keep it available.

10. Changes and contact

This policy may change as the software changes; the date at the top always says when it was last revised, and a revision applies from the moment it is published. Questions about the software or this policy go to contextator.com. Questions about the data in this installation go to whoever operates it.
